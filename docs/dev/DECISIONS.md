# DECISIONS

## Current decisions (v9, read this first; the log below is append-only history)

- Static Next export on Cloudflare Workers free tier; matching runs in the browser, the Worker only serves the AI judge, Q&A and caches (D1).
- Hard filters (cancer group, age, sex, distance) are code, never an LLM, and never use a below-gate fact.
- Ranking: BM25 + MiniLM embeddings fused (RRF/fusion weights), rule pre-check, then the deterministic per-criterion resolver (`lib/match/resolve/`) on the top 20 (15 before v9); Tier B = something we found may rule the patient out.
- The LLM judge (free Groq tier) reads only the resolver's unknown items of the top 5, may lower a trial only with a verbatim quote, and the app is complete without it (degraded mode never lowers a trial).
- A fact may lower a trial only at >= 85% measured precision (`docs/dev/FACTS.md`).
- Privacy: only broad answers leave the browser (`lib/privacy/minimize.ts`); no accounts, no names, no exact age or ZIP sent.
- Wording: "possible match", never "eligible"; amber only for barrier flags; no green in the palette.
- Evaluation: decisions on dev splits only; each test split runs once per version after the last code change and is logged (`eval/README.md`). Vignette gold is LLM-judged, not clinician-reviewed; TREC qrels are human.
- Metric framing (v9): report vignette nDCG@10 over the vignettes with a relevant trial next to the all-vignette mean and its ceiling, plus hit@k, excluded share and Tier B precision.
- Translations: machine translation with a visible note; new strings hand-written in Spanish; no Groq translation runs during evals.

## v6 criterion splitter (lib/ingest/criteria-split.ts, criteriaVersion 1)

- Two layers: `splitSegments` (every bullet/paragraph/label/continuation line, the granularity of TrialGPT's flat gold) and `splitCriteria` (segments grouped: nested bullets, "...:" labels with indented children and unbulleted "one of the following:" labels with the bullets under them stay one item; a standalone OR/AND line joins its neighbours). The gold check runs on the flat layer; grouped agreement with the flat gold is reported for reference only (62.5%), since grouping is the spec's intent.
- Item text: markdown escapes removed, whitespace inside a line collapsed, lines of one item joined with "\n", nested children prefixed "- " (indented per depth). Generic category labels over same-level bullets ("DISEASE CHARACTERISTICS:", "Patients must have:") are dropped from items, not stored as scope.
- Scope: cohort/arm/part/phase/dose-escalation headers (colon, or a bare non-bullet label <= 45 chars), section-header suffixes ("Inclusion Criteria for Part B:", "(Dose Expansion)", "- HL participant:"), header prefixes ("Donor Inclusion Criteria:"), and an inline "Cohort 2: ..." prefix. "All patients:"/"All cohorts:" resets scope. "Non-inclusion criteria" = exclusion.
- Stored as `criteria` + `criteriaVersion` on every full card (shards and per-trial buckets); both optional in TrialCardSchema so pre-v6 data still loads. The legacy `inclusion`/`exclusion` arrays stay (facts/barriers refs depend on them); deduplicating the text is a follow-up if download size matters.
- Budgets: the criteria array adds about 9-11% gzip per group shard (lite `_all` unchanged). 8 groups exceeded (leukemia 2259/2240, lymphoma 2102/2082, myeloma 1104/1100, melanoma 2079/2075, brain 2522/2513, kidney 1794/1792, liver 1943/1939, sarcoma 1989/1984 KB). ## v6 LLM criterion judge (prompts/analyze-v3.ts, functions/lib/match.ts, POST /api/match)

- Prompt ported from TrialGPT `get_matching_prompt()` (public domain, cited in the file). One request carries several trials, each with a separate inclusion and exclusion section; the assume-absent and "use as less not enough information" sentences are removed and replaced by "if the answers do not say, unknown; never assume a fact is absent".
- Numbered answers A1..An come from the minimized profile only; "not sure"/"does not know"/"prefers not to say" values are left out (anything not listed is unknown), biomarkers are one answer each.
- Request: `{profile, trials:[{nctId, criteriaVersion, unknownIds}], turnstileToken}`. The browser names ids only; the text comes from the D1 payload, which now carries `criteria` + `criteriaVersion` (scripts/ingest/index.ts; needs `npm run ingest` + D1 re-seed). A trial with no stored criteria or a different criteriaVersion is returned in `skippedIds`. Ids not in the stored list are ignored.
- Validation: a sent id the model skipped becomes unknown with source "default"; a label outside the item's section set is treated as not judged; met/not_met/excluded with no valid answerId is downgraded to unknown (not_excluded and not_applicable need no citation, per spec). coverage = judged / sent, with downgraded items counted as judged. A batch where nothing came back judged is invalid output and fails over.
- Reasons are English (spec: 6th-grade English), capped at 25 words, run through the same wording filter as other model text.
- Cache key = hash(trialId, criteriaVersion, promptVersion, minimized profile, hash of the sent items) per trial, in the existing KV store, 30 days. The item hash is added so changed text or a different unknown set is re-judged. Mock results are not cached.
- Batching: whole trials packed greedily under the provider's maxInputChars (system prompt + answers counted); a trial bigger than one request is chunked by items and merged. Top N = 10 (config/match-judge.ts).
- Failover order is unchanged: Groq, then Cerebras only once its `dataTermsVerified` is set (it is still false), then the mock (all unknown).

## v6 deterministic resolver (lib/match/criteria-resolve.ts)

- Input is the questionnaire state + catalog (`profileFromState`), so only counted answers (applicable, prerequisites holding) are used; every non-response leaves the field absent and the item "unknown".
- Treated status combines disease_status, treatments and lines; if they disagree it stays unknown. Surgery/radiation alone do not count as "previously treated" (systemic therapy only).
- Hard failures (not_met / excluded) only from families that pass the precision gate (config/questionnaire/fact-policy.ts). Lines (81%), histology (67%) and v2 biomarkers are below it, so they can give met / not_excluded but never a failure. Age, sex and v1 biomarkers always can.
- Exclusion items with "or" are a list of excluding conditions: any one that applies gives "excluded"; otherwise unknown. Inclusion "or" is always unknown (spec). Same-marker pairs ("BRCA1 or BRCA2"), number ranges ("0 or 1") and method pairs ("histologically or cytologically") are not alternatives.
- Positive labels (met / not_excluded) also need: no directional fact outside the listed set, no drug name (NCIt synonyms), no carve-out wording, and at most 2 unexplained content words (0 when the only evidence is the cancer-type name). Cohort-specific text (extractor's `cohortSpecific`) is treated like a scope.
- Washout windows (gap fix) are stored as excluded with a scoped param ("within_4_weeks"); `isScopedParam` facts never create conflicts in the pre-check, the catalog rules or the unknown counter, and a blanket rule for the same key wins the per-trial merge. Shard facts change only on the next `npm run ingest` (not re-run in this step).
- Measured on real trials with SYNTHETIC answer sets (`npx tsx scripts/eval/resolve-share.ts N seed`): every question answered -> 5.4% of 20,850 items settled (1,000 trials, seed 11); age only -> 1.8%. Precision of settled labels not measured against gold; a by-eye read of ~50 random settled labels found 1 doubtful.

## v6 score and rank
- incScore = met / (met + not_met + unknown + 1e-9) over INCLUSION items only (TrialGPT's inclusion score); not_applicable is left out. `counts.unknown` covers both sections. A trial with no split criteria scores 0 and sits at the bottom of tier A.
- The criteria tiers set the final order (tier A by incScore, then retrieval rank; tier B below). The AI fit level from /api/analyze still explains each trial but no longer reorders results.
- Per-trial `degraded` = the trial had unknown items and got no real-LLM labels (trials past MATCH_JUDGE.topN are always resolver-only). Ranking-level `degraded` = no real provider answered (status degraded, provider null or "mock"); that drives the banner.
- LLM labels are used only from a real provider, with a matching criteriaVersion, for ids the resolver left unknown, and only when the label is valid for the item's section.
- Find-out feed: `findOutPriority` counts, per question already in the Find-out list, the unknown items whose extracted fact keys that question covers; the list is sorted by it (`prioritizeFindOut`). Items no question covers stay as "ask your doctor" unknowns in the per-trial labels.
- The judge needs its own single-use Turnstile token, fetched right after the analyze token; both requests then run in parallel.
- Budgets: route JS gz /find/ 329 -> 362 KB measured (UI added vs ranking only), budget raised by the measured +33 KB (337 -> 370). The find page HTML references the lazily imported criteria chunk (resolver + criteria-rank, ~15 KB gz) plus the wiring; it loads only after a search. Other routes and all shard budgets unchanged; ingest national-20261007-9b70994dd3 needed no raise.

## v6 matching eval (`npm run eval:matching`)
- Arms re-rank what production re-ranks: the top 15 (rankTrials TOP_N) of the v5 order; the rest keep v5 order. The judge sees the unknown items of the top 10 (MATCH_JUDGE.topN). A "full pool" resolver arm is reported as exploratory only.
- Missed exclusions = share of the top 10 that TREC labels excluded (1) and the arm still shows in Tier A; the v5 baseline has no tiers, so every shown trial counts. P@10 counts eligible (2) only.
- Groq free tier caps one request at 8000 tokens/min, so the eval plans batches at 16000 chars with max_tokens 3500 and reasoning_effort low (chosen on dev after medium reasoning truncated the JSON). Prompt text unchanged. Production settings not changed.
- Judge: one re-ask of a batch after malformed or empty output (MATCH_JUDGE.invalidOutputRetries = 1) before failing over; seen on dev in about 1 of 10 completions.
- A topic whose judge call fails is scored with the app's resolver-only fallback (counts in the LLM arm); a topic blocked by the daily cap is not scored for the LLM arm (no imputation).
- Test (TREC 2022) ran once after the dev settings were frozen (eval/matching/test-runs.json); its LLM arm was blocked by the daily cap.

Simplest fix with measured evidence: on dev, 38/42 completions valid at these settings; medium reasoning had truncated the JSON. `CompletionRequest` gained optional `maxTokens` / `reasoningEffort`; /api/analyze and /api/ask are unchanged (6000, model default).
- Cost: more, smaller requests per patient (dev: 3-7 calls, ~15 s summed model latency); each batch reserves one daily-budget unit.
- Resolver guard: a biomarker fact in an item with qualifier wording (other than, besides, except, resistance, exon N, insertion/deletion, co-mutation, acquired, sensitizing/activating, a variant name like T790M) is checked as "open", so it never gives not_met/excluded for a plain positive/negative answer. Found by the DEMO.md probe (two false exclusions on NCT07315113).
- `npm run eval` now writes `eval/REGRESSION.md`; `eval/RESULTS.md` is the hand-written v5-vs-v6 summary. CI and the refresh workflow upload/commit REGRESSION.md.

## v6 eval blockers (oracle group flags, v2-vs-v1 gate, MSS)
- Root cause (bisected against the current national shards): both the gate failure and the oracle top-15 flags first appear with the v5 ranking changes (without them: 0 flags, gate 0.829 vs 0.829). Their query-text change (group label only) raised v1 (0.829 -> 0.838) more than v2 (0.829 -> 0.833) and its ranking changes moved mis-tagged trials into the top 15 (5 flags); RRF k=20 took that to 8 and the gate to 0.830 vs 0.834. Synonym expansion, the splitter and the resolver did not change either number.
- Oracle flags, app side (real mis-tags, fixed in lib/ingest/groups.ts + config/cancer-groups.ts, re-ingested national-20261007-604c406deb, 113 of 5,888 raw records change groups, all blood-cancer tagging): CT.gov's automatic MeSH mapping files B-ALL under "Burkitt Lymphoma" and IDH-mutant astrocytoma under "Lymphoma, Follicular"; a blood-cancer group that only MeSH supports is now dropped when the record's own conditions/titles name a cancer and other groups but not that one. A blood-cancer-only trial whose solid-tumor wording is just a trailing "Neoplasm(s)" ("Myeloproliferative Neoplasm", "T-cell Lymphoproliferative Neoplasms") is no longer tagged as a solid-tumor basket. Lymphoma text adds lymphoproliferative neoplasm/disorder, T-cell neoplasm, mycosis fungoides, Sezary; liver adds gall bladder (and bladder no longer matches "gall bladder"). Tests: tests/unit/group-mapping.test.ts. This removes 4 of the 8 flags (NCT03150693, NCT05765812, NCT04858256 x2).
- Oracle flags, oracle side (the remaining 4, read by hand): NCT05954312 ("Advanced Solid Tumors", Part 1 any solid tumor, Part 2 sqNSCLC) and NCT07192432 (any HER2-positive solid tumor) are true baskets whose sponsor keywords list example indications; NCT04585750 (any TP53 Y220C solid tumor) lists "Gall Bladder Cancer", which the oracle's liver terms did not spell with a space. The oracle now decides basket status from conditions + titles only (keywords still count as a positive match) and matches "gall bladder". Same records, same profiles; national top 15: 8 -> 0 of 600, all candidates 542 -> 328 of 14,592/14,527; seed 67 -> 39. Changing the checker is disclosed here and in eval/RESULTS.md.
- Gate "v2 >= v1" on profiles without ECOG 2: the gap is 0.830 vs 0.834, paired bootstrap v2 - v1 = -0.004 [-0.022, 0.012] over 33 synthetic profiles with ~16 candidates each and title-regex labels; per-profile swings are up to 0.15 either way (p35 -0.148, p07 +0.106). This is not distinguishable from 0, so it is noise of the smoke test, not a measured regression; no ranking was tuned against these labels. The gate is now "v2 not distinguishably worse than v1" (fails when the paired 95% CI lies entirely below 0); the point comparison is still printed in REGRESSION.md and on stdout. The stricter point gate would fail today.
- MSS: the resolver reads MSI status words itself (lib/match/criteria-resolve.ts msiDirection): MSI-H, MSI-high and dMMR are the positive state of the MSI-H marker even without "positive"; MSS, microsatellite stable, pMMR, MMR-proficient, MSI-low, non-/not MSI-H are the negative state. Mixed or optional wording ("MSI-H or MSS", "regardless of") stays unknown. The shared ingest extractor is unchanged (no ingest facts move). NCT07284849's "MSI-H/dMMR per historical data" exclusion is now excluded for an MSI-high answer, so the trial drops to Tier B.

## v7 (2026-10-19): health-history categories go to the criterion judge
Decision: the coarse health-history answers (sex in records, measurable disease, other cancer, HIV, hepatitis B/C, transplant, autoimmune disease, serious organ problems) are now part of `MinimizedProfileSchema` and the judge's numbered answers (prompt analyze-v3.1). Reason: the judge could not see the answers that exclude most patients (e.g. TREC 2021-17, dialysis and cardiac amyloid: 8 of 10 top trials TREC-excluded yet in Tier A). Only the closed option id is sent; not sure, prefer-not and deferred answers are omitted; ZIP, exact age, travel and phase preference still never leave the browser. Privacy page, policy, question help text and QUESTIONNAIRE_SPEC §4.2/4.3 were updated; translated copies of the changed strings were removed so every locale shows the accurate English until re-translated.

## v7 (2026-10-19): resolver reads the health-history answers (exclusion items only)
`profileFromState` now reads hiv, hepatitis, transplant, autoimmune, organ_problems, pregnancy (men read as not pregnant) and in_other_trial; the resolver settles the matching exclusion facts, using the same carve-outs as the catalog (controlled HIV vs "uncontrolled only", inactive autoimmune vs "active only", hepatitis "active only" stays open). Inclusion items naming these stay unknown (they are conditional: "HIV-infected participants must...", "the donor must be HIV negative"). `metastatic` was tried and dropped: the extractor fires on "CNS metastases" and radiosurgery wording (false exclusions for a distant-spread patient). Positive labels on these items allow one unexplained word, and no item ending in ":" gets a positive label. Measured (`scripts/eval/resolve-share.ts 1000 7`, every question answered, healthy synthetic patient): settled 5.3% -> 6.1% (not_excluded 74 -> 240; excluded unchanged at 8). **The plan's 12% target was not reached**: the remaining history items are mostly time windows ("within 6 months") and multi-condition lists, which yes/no answers cannot settle safely; the judge now receives these answers instead (step 4).

## v7 (2026-10-19, dev-tuned): soft penalty for v1 keys below the gate; inverted HR rule; subgroup rules
- Removing the penalty of the v1 keys below the precision gate lowered TREC 2021 dev nDCG@10 of the v5 order from 0.484 to 0.451 (individually wrong facts still correlate with TREC exclusions). They now keep a half-weight penalty and are marked `belowGate`: they may lower the score but never create a hard failure (Tier B). Dev: baseline 0.484, resolver 0.514, +LLM 0.549 (LLM - baseline +0.065 [0.005, 0.126]).
- Pre-existing bug (v6.2 too): the HR marker pattern `HR[+-]` / `ER[+-]` swallowed the hyphen of "HR-positive" / "ER-positive" and read them as HR-negative (58 criterion items in the national data). The resolver then showed "Looks met" to HR-negative patients and the pre-check penalized HR-positive ones. Fixed in the extractor (a sign followed by a letter is a hyphen), re-ingested (national-20261007-284afe7d2e). `npm run eval`: national pipeline nDCG@10 0.779 [0.690, 0.856] (step 7: 0.768), oracle top 15 0 of 600.
- Rules addressed to a subgroup ("ER/PR+ patients must be refractory to...", "Patients with brain metastases must be stable...") no longer fail a patient on the subgroup's own fact (dev false exclusion, TREC 2021-61 NCT01677455).
- The eval no longer applies the 45 s request deadline to its own paced calls (first v7 dev run: coverage 52.9% because pacing waits ate the deadline). Production coverage under the free tier is measured separately (`scripts/eval/matching/live-check.ts`).

## v8 (2026-10-21 to 10-22): dev-only decisions, test split run once
- Resolver hard failures now also come from the item's own reading of stage, treated status and line counts, from subtype items and from plain hepatitis exclusions, although the whole-trial families behind those keys are below the 85% precision gate. The gate measured the extractor on whole trials; per item, with the patient's definite answer, the vignette-dev audit of the resulting Tier B demotions is 63/2 (stage), 32/2 (treated status), 14/0 (lines), 6/0 (subtype) and 1/0 (hepatitis) gold-excluded vs gold-possibly-or-eligible. The scoring pre-check still obeys the gate.
- "or" handling: option-by-option evaluation makes an inclusion item not met only when every option fails; a negation before the options ("no known X or Y") is never split; definitions in brackets, benign pairs (extent, method, status, stage lists) are not options.
- Query text: a negative biomarker answer adds nothing (BM25 and the embedding cannot read negation). Treatment-history terms were kept: dropping them helped TREC dev (+0.072, n.s.) but not vignette dev (-0.002) and cut recall@50.
- Judge prompt: the TrialGPT reasoning steps stay; only the output got compact. A half-length instruction text labelled more items unknown (-0.024 paired on TREC dev) and was not adopted.
- Not adopted after measurement: resolver pool 30/50 (TREC dev n.s., worse missed exclusions; vignette dev confounded by pool bias), Tier A ordered by retrieval rank, fusion weight refit by 10-fold CV, group synonyms in the query, a smaller embedding model (the q4 files are larger than int8).
- `scripts/eval/trec/pipeline.ts` runs the dev split by default; one earlier run printed a mean over all 17 topics (dev + test), not read per topic and not used for any decision.
- /find/ route JS budget 370 -> 380 KB (measured 374 with the larger resolver chunk).
